## 业务开发规范标准

*最后更新: YYYY-MM-DD*
*版本: vX.Y.Z*

### 规范定位与优先级

- **适用范围**: 本规范约束业务层实现（模块划分、状态流转、表单校验、API 集成）；通用层规范约束命名、类型、导入、格式与性能
- **优先级**: 仓库内规范 > 本规范 > 默认约定；不同仓库在同一议题上允许有不同约定
- **例外**: 设计稿或既有系统习惯明确要求时，以既有约定为准，并在代码中说明原因
- **查证**: 具体包名、路径、组件、i18n 入口与构建工具，一律以当前仓库配置为准，先查证再使用

### 多端与多主题配置

- **双平台实现**: 同一组件在 `m/` 与 `pc/` 各保留一份实现，接口保持一致，实现各自优化；移动端优先考虑触摸、手势与虚拟滚动，PC 端优先考虑 hover / focus、键盘导航与大屏
- **主题继承**: 基准主题定义全量基础配置，其他主题只写差异项；配置取值按「子主题 > 父主题 > 默认值」逐级回退
- **配置文件**: 每个主题目录固定包含基础信息（标识、名称、描述、缩略图）、`comps-pc.ts` 与 `comps-mobile.ts`
- **优先级校验**: 覆盖顺序必须写入规范并配测试用例，避免退化为「谁后加载谁生效」的隐式行为
- **禁止**: 新增主题时复制全量配置；禁止在子主题中重复定义与基准主题相同的取值

```
tmpl/
├── base/                    # 基准主题，唯一完整定义
├── example-theme-a/         # 只写覆盖项
└── example-theme-b/         # 只写覆盖项
```

### 组件分层与可配置属性系统

| 分层 | 职责 | 判断标准 |
| --- | --- | --- |
| `core` | 无业务语义的基础 UI（Button、Input、Modal） | 换任何业务都能复用 |
| `pro` | 带业务语义的组合组件 | 依赖具体业务流程或数据结构 |
| `style` | 主题系统与设计变量 | 不含交互逻辑 |
| `icon` | 图标资源 | 独立发布 |

- **属性映射**: 每个可配置属性的 `propType` 必须能映射到属性面板中已存在的表单项类型（text、number、color、select、switch、slider、image 等），新增类型前先确认表单项已支持
- **跨仓库契约**: 组件库新增配置字段与编辑器新增表单项必须成对变更
- **实时预览**: 属性值变更必须即时同步到预览，禁止等保存后才生效
- **Props 设计**: 相同功能的属性在不同组件中命名一致；新增属性不破坏既有 API；提供合理默认值，减少必填项

### 可视化配置页面

- **模块划分**: 顶部栏（信息展示、终端／页面／市场切换、撤销重做、保存）、左侧栏（入口切换）、中间面板（随入口切换）、右侧属性面板（当前选中项、实时预览）、中央预览（拖拽排序）
- **跨窗通信**: 与预览 iframe 使用 `postMessage`，选中态单向同步，禁止两端各存一份真相
- **历史记录**: 状态变更走不可变更新；历史记录设上限（如 50），超出丢弃最旧；任何变更标记为已编辑；页面离开时清空状态
- **键盘操作**: 支持撤销 / 重做快捷键；实时模板的保存动作需要二次确认

```
editor/
├── index.tsx                # 主入口，负责初始化与模块编排
├── store.ts                 # 编辑器状态
├── type.ts                  # 业务实体类型
├── apis.ts                  # 接口定义
├── use-tmpl.ts              # 模板数据处理
├── common.ts                # 通用工具与常量
└── header/ side-bar/ panel/ attrs/ preview/
```

### 表单开发

- **必填校验（P0）**: 设计稿标注星号的字段必须逐条添加 `required: true`，并给出明确到具体操作的提示信息；禁止只写 `{ required: true }` 而不给提示
- **选项顺序（P1）**: 是／否、开／关等二元选择遵循「否定在前、肯定在后」，设计稿或既有习惯另有规定时除外
- **交互收口**: 确认操作走统一确认弹窗；消息提示走统一全局实例；网络错误集中在失败回调处理；加载态使用组件自身的 `loading` 属性
- **小屏适配**: 属性面板等辅助区域在小屏下可隐藏，主操作路径保持可用

```tsx
// ✅ 正确：必填校验 + 明确提示 + 选项顺序
<FormItem
  label={t('是否启用展示')}
  name="enableDisplay"
  rules={[{ required: true, message: t('请选择是否启用展示') }]}
>
  <RadioGroup>
    <Radio value={0}>{t('否')}</Radio>
    <Radio value={1}>{t('是')}</Radio>
  </RadioGroup>
</FormItem>

// ❌ 错误：漏校验 / 无提示 / 顺序相反
<FormItem label={t('是否启用展示')} name="enableDisplay">
  <RadioGroup>
    <Radio value={1}>{t('是')}</Radio>
    <Radio value={0}>{t('否')}</Radio>
  </RadioGroup>
</FormItem>
```

### 请求层与 API 集成

- **统一入口**: 所有请求通过统一封装的请求 Hook 管理，由它负责 `data` / `loading` / `error`，业务代码只声明触发方式与生命周期
- **类型来源**: 请求与响应类型由代码生成工具产出并集中存放；禁止手写 `any`、禁止手写响应结构
- **生命周期**: 请求前／成功／失败三段共同负责加载态的显示与关闭，每个出口都必须收尾
- **错误分类**: 网络错误、业务错误、权限错误分开处理，提供友好提示与重试入口

| 模式 | 配置 | 适用场景 | 易错点 |
| --- | --- | --- | --- |
| 自动 | 默认执行 + `ready` + `refreshDeps` | 页面加载即取数 | 依赖登录态或 ID 时漏写 `ready`，发出无效请求 |
| 手动 | `manual: true` → `run` | 按钮点击、表单提交 | 漏写 `manual: true` 导致自动多执行一次 |
| 异步 | `manual: true` → `runAsync` | 需要 `await` 结果再继续 | 对 `run` 使用 `await`（它不返回 Promise） |

```ts
import { useRequest } from '@example/hooks'

// ❌ 错误：成功分支忘记收尾
const { run } = useRequest(submitExample, {
  manual: true,
  onBefore: () => showLoading(),
  onSuccess: () => notify('Saved'),   // 漏了 hideLoading()
})

// ❌ 错误：对不返回 Promise 的触发函数使用 await
const { run } = useRequest(fetchExample, { manual: true })
await run()

// ✅ 正确：需要等待结果时使用异步触发函数
const { runAsync } = useRequest(fetchExample, { manual: true })
await runAsync()
```

### 样式与国际化

- **样式隔离**: 使用模块化样式或样式函数，确保组件间不互相污染
- **Token 优先（P0）**: 颜色、间距、字体、圆角一律取自设计变量；禁止硬编码颜色值与魔法数值
- **工具复用**: 文本省略、隐藏滚动条、粗体等效果优先使用既有 mixin，禁止重复实现
- **国际化（P0）**: 所有用户可见文本必须通过统一入口处理，禁止直接写死文案；新增文案需同步考虑语言环境上报
- **多主题回退**: 主题切换支持运行时生效，并提供默认主题作为兜底

### 组件文档与 Demo

```
example-component/
├── src/
├── demo/
│   ├── basic-usage.tsx       # 基础用法
│   ├── advanced-usage.tsx    # 高级场景
│   ├── data.ts               # 模拟数据
│   └── mock-apis.ts          # 模拟请求（带延迟）
└── index.md                  # 组件文档入口
```

- **数据分离**: 不同类型的模拟数据分文件存放，禁止堆在示例页面中
- **状态覆盖**: API 模拟必须覆盖成功 / 加载 / 失败三类场景；使用 Promise + 延迟模拟异步
- **可观测性**: 重要事件与请求在控制台留有输出，便于调试
- **文档完整**: 逐项列清必需属性、可选属性及默认值、事件回调的参数与触发时机、方法签名与返回值

### 状态管理与性能

- **状态更新**: 使用不可变更新；状态变更标记编辑状态；页面离开时清理，避免脏状态串场
- **渲染优化**: 合理使用 `memo` / `useCallback` / `useMemo`；长列表使用虚拟滚动；大型组件支持懒加载
- **打包优化**: 支持按需导入与 tree shaking，合理做代码分割与缓存

### 版本与变更记录

- **语义化版本**: 主版本号用于不兼容的 API 修改，次版本号用于向后兼容的功能新增，修订号用于问题修正
- **发布流程**: 版本检查 → 构建测试 → 更新变更记录 → 发布
- **变更记录格式**: 按「新增 / 修复 / 变更」三类分组，每条注明影响范围

```md
## [vX.Y.Z] - YYYY-MM-DD
### 新增
- 新增组件的 loading 状态
- 支持自定义主题配置
### 修复
- 修复弹层层级问题
- 优化移动端触摸响应
```

### 同一体系内的差异化约定

同一体系内不同仓库在以下议题上允许各自生效，不追求跨仓库一致，只要求单仓库内一致：

| 议题 | 前台业务仓库 | 组件库仓库 | 管理后台仓库 |
| --- | --- | --- | --- |
| 样式方案 | 模块化样式 + 设计变量（`$variable`） | 样式函数 + 设计 token | 模块化样式 + 条件类名工具 |
| 国际化入口 | 开发期占位，上线前替换 | 未规定 | `t()` 直接传中文（P0） |
| 请求 Hook 来源 | 基于社区库自封装 | 组件库自带 hooks | 平台级扩展库 |
| 组件文件命名 | 小写 kebab-case | 小写 kebab-case | 局部模块使用 PascalCase |

- **冲突处理**: 以仓库内规范优先于通用层规范；新增代码先参考同类既有实现，跟随既有习惯
- **依据说明**: 与既有约定不一致的实现，需在代码中说明原因
