# 你的编程智能体，把你变成了管理者

![图像](https://pbs.twimg.com/media/HWfhdJTasAAa-X_?format=jpg&name=large)

管好智能体需要的本事，和带好一支团队几乎是同一套；而这套本事，不必先当上管理者才能学会。

如果你一整天都泡在编程智能体旁边，你就是在做管理。挑任务、写指令、把活派出去、跟进、验收结果、拍板什么能上线——这些事你一遍遍地做。把智能体用得最透的工程师，未必是最懂提示词工程的那批，而是有意无意间学会了「怎么管」的那批。

这话可能不太中听。我欣赏的不少工程师之所以走个人贡献者（IC）这条路，就是想离具体的活儿近一点；他们见过朋友升了管理者之后，整个人消失在日历里。但我不是劝你去当那种管理者。我这里说的「管理」是个窄得多的意思：靠让别人把活干成，来拿到好结果。当然，我也绝不是在说智能体能替代管理者或同事。

你对糟糕管理者的每一条抱怨，其实都是一份关于「怎么跟智能体打交道」的 bug 报告。拿交接来说：一次糟糕的交接，可能是需求含糊、没给背景，或者期望一变再变。对 IC 来说好消息是——你这些年一直在交接的接收端，好的交接长什么样，心里其实有数。

我此前写过[《你的编程智能体需要一个管理者》](https://addyosmani.com/blog/coding-agents-manager/)，也写过委派里那个不易察觉的风险——[「认知让渡」](https://addyosmani.com/blog/cognitive-surrender/)。这篇把优秀工程管理者的做法，和我们做 Claude Code、用 Claude Code 过程中学到的东西摆在一起对照。各节大体按影响力排序，杠杆最高的习惯放在最前面。

## 给它一套自检机制

**最佳实践：**给智能体一个能验证自己产出的机制——测试套件、构建、截图都行——并让它把结果摆出来当证据。

**反模式：**把「看起来做完了」当成确认。结果是所有验证都落到你头上，你成了智能体的测试套件。

去问一个老练的管理者：不逐份看，怎么确信团队产出是靠谱的？他会跟你聊护栏——CI、代码评审、监控面板、值班轮值等等。新手管理者不搭护栏，最后什么都得自己验，一个季度不到，自己就成了瓶颈。智能体也一样。[Claude Code 最佳实践指南](https://code.claude.com/docs/en/best-practices)里讲得很直白：活儿「看起来做完了」，智能体就停了；没有验证手段，「看起来做完了」就是它唯一的验收标准。给它一套验证机制，它就能自己干活、自己跑校验、自己看见失败、自己改回来。改 UI 的话，这一步可以是真的在浏览器里把页面打开，反复调到能用、能看为止。

验证机制几乎可以是任何东西，只要它给出非黑即白的通过／失败：测试、构建退出码、linter、diff 脚本、截图都算。指南里特别提了一句：把这些校验跑起来的那条命令，是 `CLAUDE.md`（智能体每次开会话时先读的指令文件）里最值钱的一行。有了验证机制，可以这样把它嵌进流程：

- **直接要求。**「改完跑一遍 auth 相关测试，没过就继续修到过。」
- **设目标。**用 `/goal`，让另一个模型在每一轮之后检查条件是否成立；跑长时间的后台任务时最有用。
- **强制卡住。**用 Stop hook，类型检查不过就不让这一轮结束。
- **交给别人审。**`/code-review` 会把 diff 发给一个没看过你们对话的新子智能体去审——就像作者不该批准自己的 PR。

连审查的范围你都能框住。只说「找问题」，它总能挑出点什么；说「只找正确性问题、别管风格」，它就真的只找正确性问题。好的管理者也是这么学会要反馈的。Claude Code 工具箱里大部分功能，都是在收紧这个回路：Skills、hooks、子智能体和 MCP，都是为补上「干活」与「验活」之间那段空隙而存在，好让你的注意力只落在智能体验不了的地方。这正是老练的工程管理者在做的事。

## 把上下文交代清楚

**最佳实践：**把智能体翻遍代码仓库也无从得知的东西讲清楚：这次任务要达成什么、为什么重要、有哪些约束、什么不归它管、以及怎样算做成了。

**反模式：**只丢一句话过去，真正的期望全留在自己脑子里；或者反过来，把智能体读一遍代码就能发现的细节塞满说明。

有效的管理者会把想要的结果、边界和目标讲清楚，但把「怎么做」留给干活的人自己定。军队里管这叫「指挥官意图」（commander's intent），Netflix 的说法是「给上下文，不给控制」（context, not control）。

跟智能体协作难就难在：你不容易知道它缺的是哪块上下文。它每接到一个任务，第一件事是读你的代码。现在的模型摸清目录结构、代码约定、测试配置的速度，比你描述一遍快得多。

所以动笔之前先想一想：哪些它自己能弄明白。凡是能在代码里读到、而且它确实会去读的，就不用写。把字数花在仓库里没有的东西上——比如某次会上定的结论、某个人内部的上线流程、这活儿为什么重要、这一次「做完」具体指什么。

拿一句含糊的任务「把仪表盘弄快一点」做例子，把它改写成一条像样的指令。下面的数字只是举例。

```bash
让 /team 仪表盘在 1 万以上成员的组织下，p95 加载时间降到 2 秒以内。

为什么：企业管理员每天都开这个页面，加载慢是他们工单里排第一的问题。

约束：不改 schema；保持 API 响应结构不变。

不做什么：不动 UI；不做整页缓存。
验收：跑 scripts/perf/team.sh，给出优化前后的数字。
```

不必每个任务都这么写。探索阶段的任务，指令笼统一点完全没问题，边走边收窄就是了。要是你自己还没想清楚到能写指令，就让智能体反过来采访你，问到它能把规格写出来为止，把这份规格存成文件，再开一个新会话让它照着规格开工——后面还能拿它当验收依据。

你可能还得给它接上别的工具：工单系统、错误监控面板、团队聊天。把它当团队里刚来的新人对待就行。至于它本来就认识的命令行工具（比如 `gh`），通常一个字都不用多说。

## 让每次纠错都能复利

**最佳实践：**同一件事纠正过两次以上，就写进团队共用的 [CLAUDE.md](http://claude.md/)，或者做成一个共享 skill。隔一段时间再回头看看：新模型出来后，这些纠正是不是已经不需要了。

**反模式：**每次开会话都手动纠正同一件事；或者依赖只存在自己机器上、谁也没写下来的默契。

把 `CLAUDE.md` 用出价值的团队，会隔一阵就更新一次，把值得防第二次的教训记下来。有的团队甚至在代码评审里 [@claude](https://x.com/@claude)，把一条反馈直接变成长期规矩。`CLAUDE.md` 要短，值得写进去的是这几类：

- 怎么验证（精确到命令）
- 代码里容易看错、容易误导人的地方
- 仓库里查不到的决策
- 任何你纠正过两次的事

这些都在说明同一件事：写下来的信息会复利。人换组、模型换代，它都还在。

## 默认让它自己定，只强制不能让步的部分

**最佳实践：**默认让智能体自己拿主意；只有那少数「必须发生」或「绝不能发生」的事，才动用 hooks、deny rules 这类硬手段。

**反模式：**用全大写写规则；给可有可无的偏好也配上 hook；或者新模型早就不需要了，还留着为旧模型养成的习惯。

安迪·格鲁夫（Andy Grove）在《高产出管理》里管这叫「任务相关成熟度」（task-relevant maturity）：该管多严，取决于这个人在**这件具体任务**上一贯的表现，而不是他的总体能力。

给新管理者的一句老话说的也是这个：给人的余地要比你自己觉得舒服的再多一点，同时在背后兜着底、该追的责照追。

Claude Code 把这条做成了明确的机制：指令、`CLAUDE.md`、skills 是「请求」——模型可以权衡、可以选择照做；hooks、deny rules、托管设置是「要求」——无条件执行。多数情况下，你希望由它来判断。它看着真实代码，往往比你事先写死的一条规则更有资格判断这条准则此刻适不适用。强制手段只用来立硬规矩，比如「绝不手改生成的客户端」「每次都跑许可证头脚本」。另外，新开的终端和 VS Code 会话默认进 auto 模式，由一个分类器挡掉危险动作，例如直接发到生产环境、或者强推覆盖别人的提交。

指南里的建议是两面的：如果 `CLAUDE.md` 某一行你反复加粗强调，智能体还是不买账，那它就该升级成 hook；反过来，如果一个 hook 表达的只是偏好而非硬要求，就该删掉，把决定权还给智能体——就像团队决定废掉一套已经没用的流程。换了新模型，同样要重新调。指南里列了一份「可以停掉的习惯」：全大写的祈使句、「think harder」（现在思考力度是个配置项）、「别偷懒」。在当下的模型上，这些多半只会换来过度强制的规则和一堆多余动作。放到智能体身上，流程过剩就是新版的微观管理。

## 先定计划，再让它动手

**最佳实践：**动手写代码之前先把计划对齐；读计划时重点看底下没说出口的假设；拆任务时切成互不重叠、能并行推进的块。

**反模式：**让几个智能体同时扑在互相重叠的任务上，然后花一下午收拾合并冲突和重复拍板。

一个顺手的流程是：先进 plan mode，把计划来回改到对为止，再把编码派下去。计划够好，模型常常一遍就能全做出来。任务更大时，另开一个会话，让它以资深工程师的眼光把计划过一遍——这就是设计评审，也是发现「走错方向」最便宜的环节。看计划时要盯那些藏在底下的假设（换成一对一沟通，你问的就是「哪一块你还没把握？」）。

连拆活这件事，也越来越多地交给智能体了。Claude Code 的 `/batch` 能把一次大规模的机械式改动拆成 5～30 个任务，先把计划摆给你看，再放进各自的 worktree（各自独立的仓库检出）里执行，每个任务出一个 PR。你不用再自己切分，只要检查各块有没有重叠、确认共用接口先落地。少了这一步，你得到的只是虚假的并行度：五个智能体抢着重叠的活，不会换来五倍产出，只会换来一个由五个人共同署名的合并冲突。

## 早纠偏，两次不成推倒重来

**最佳实践：**头一分钟盯着点，及时拨方向。一看它跑偏就纠；如果已经连纠两次都没纠回来，别再纠了——开个新会话，重写一条更好的指令。

**反模式：**接着追加第三次、第四次纠正，而不是回头改那条需求本身。

老练的管理者知道：一个能干的人反复失手，问题多半在上游——指令、上下文或者范围没给对。换成智能体，这条更直白：一偏就按 Esc。连纠两次还不行，就清掉会话，把这轮学到的东西写进新指令重来。第三次纠正，本质上只是又往上下文里塞了一份模型得反复重读、反复处理的信息，而且里面还夹着前两次的失败记录。

回滚变便宜，也在改写打法。`/rewind` 能把代码和对话一起退回早先某个点，于是先试一把更激进的方案也变得没什么风险。好的管理者对下属也是这样：撤销错误代价很低，就让他放开手试。事后照常复盘，能提炼成通用规则的，再写进 `CLAUDE.md`。

## 委派任务，别委派判断

**最佳实践：**活让智能体干，重要的事你来定：产品取舍、安全边界、什么能上线。看每一份 diff，都当作半夜会因为它被叫起来处理故障。

**反模式：**因为测试全绿、命名看着也像样，就批掉一大坨 diff。这不叫代码评审，这叫「代码追认」（code ratification）。

没有哪个管理者能说「那是我下属发的，跟我没关系」。你跑的每个智能体也一样。这个坑我自己踩过：我让一个智能体去调研跟竞品的差距，再写本地 PR 把差距补上。调研我读了，代码扫了一眼，差点就把改动推上去——那些改动给用户添了复杂度，收益却寥寥。我把活委派了出去，也差点把判断一起委派出去。这坑太好掉了：600 行的 diff、命名看着合理、测试全绿，批。

按这个思路分工是合理的：格式风格、lint、评审意见的收尾、常规 bug、单元测试交给智能体；安全边界、合规、产品决策留给人。

协调也一样。智能体可以替你记着交接到了哪一步，但在互相冲突的诉求之间做取舍、让人真的拍板承诺，仍是人的活。

你不必待在每次改动的内层循环里；但外层循环必须握在自己手上：约束是什么、产出你究竟读了多少、留下哪些证据、哪些环节必须有人签字。还有，把改动做小——审查的单位，得是人能真正理解的单位。

## 设计一场不需要你在场的运行

**最佳实践：**放一个自主任务跑起来之前，先把这几样定死：什么算完成、它怎么自验、边界在哪、护栏是什么、哪里要人来批。

**反模式：**睡前丢一个长任务出去，既没定义「完成」，也没设停止点；第二天醒来发现模型基于一个错前提干了一整夜。

隔级管理者（skip-level manager）管的不是单个工程师的活，是目标、护栏、检查点和各条线的负责人。AI 智能体正沿着类似的轨迹走：它们已经在把任务的一部分再派给子智能体，也能按定时计划、CI 失败、新 PR 打开这些事件自主启动。再往前，是能自己启动、自己验证、只在需要拍板时才叫人的自治系统。

角色于是从「控住这场会话」变成「设计好你的回路」。设计一次无人值守的运行，要问自己的五个问题，和一位好管理者把项目交给资深工程师、然后自己休假去之前问的一模一样：

- **它知道「做完」长什么样吗？**（目标条件、规格文件，或者一个必须由它跑绿的失败测试。）
- **它有自验机制吗？**（测试套件、Stop hook，或一道评审环节。）
- **它的边界在哪？**（权限控制、沙箱、worktree，或者只允许推某一个分支。）
- **护栏是什么？**（轮数上限、花费上限。）
- **产出落在哪里、谁批？**（一个 PR 或一份摘要；任何不可撤销的操作都要人点头。）

指南里还有两条，管理者一眼就认得出是好习惯：一是先试点——批量任务先拿三个文件跑，把指令调顺了再跑剩下的；二是任何新流程，先盯着头几次运行，再放心让它无人值守。就当是给它一段试用期。

## 扩展验证能力，而不是扩展注意力

**最佳实践：**智能体用到多大规模，取决于检查、目标，以及带着全新上下文的评审者能替你接下多少盯梢的活；除了吞吐量，也要量质量。

**反模式：**开的会话多到自己审不过来；拿 AI 写了多少代码当成功指标。

管理者很快就能摸到自己的管理幅度：直接下属一过某个数，每个人分到的注意力就变少，质量跟着往下掉。智能体也一样。我管这叫「编排税」（orchestration tax）：过了头几个之后，每多一个智能体，要占用的注意力都比上一个更多。我多数日子同时跑四五个后台智能体加几个本地会话，有些日子这已经嫌多了。

管一大堆会话，靠的不是格外专注，而是把大部分盯梢外包给自评、目标和全新上下文的评审者，把注意力留给决策。另外，用通知代替反复去刷、把后台任务集中到一个视图里，也很有用。智能体的数量，没法靠「盯得更多」扩上去，只能靠「需要盯的更少」。再往下，要量的是系统，不是活动量：PR 从开到合的周期、新人上手所需时间、回滚与返工的频率，都是有用的指标。量「AI 写的代码占比」不是个好目标，因为你真正要的是质量和可靠性。格鲁夫那条「有指标就要有制衡指标」的规矩在这儿同样成立：如果你统计合并的 PR 数，就得同时统计回滚和返工。

## 想清楚什么不做

**最佳实践：**问清楚谁需要、怎么才算奏效、什么情况下该停手；同时控制在制品（WIP）数量。

**反模式：**反正做起来便宜，把每个看着可行的点子都塞进 PR。于是团队多了一个杂物抽屉，得替它评审、替它做安全、替它长期维护。

管理者最要紧的一个词，常常是「不」。有了智能体，这个「不」更难说出口：开工几乎不花钱，中午之前你就能把任何看着可行的点子变成一个 PR。可接下来，是一堆需要团队评审、加固、支持和维护的 PR。现在稀缺的是评审和验证，不是代码。

那些老掉牙的管理问题，如今反而比过去更要紧：谁提的？成功怎么量？什么时候该收手？当「做」变得便宜，难回答的就不再是「能不能做」，而是「该不该做」。

## 这个类比在哪里失效

**最佳实践：**照着管理的成熟做法走，但要把智能体这套模型的不同算进去：返工极便宜、太容易顺着你、能力长短还随每次模型发布而变。

**反模式：**把智能体当成一名初级工程师；或者因为能同时跑五个智能体，就觉得自己已经能带五个人。

这个类比好用，但不严密；真正把这件事做明白的人，都清楚它不严密在哪：

- **管人更难，而且本事不能反向迁移。**跑过五个智能体，不等于你能带五个人。激励、冲突、职业发展、花几个月建立信任——这些在智能体身上没有对应物。
- **返工几乎不要钱。**有些事你绝不会开口让同事做，却可以让智能体做。白板前争不出结论的技术方案，让它把两三个版本都做出来，摆在一起比就行。
- **智能体没有经验，只有一个笔记本。**auto memory 只在单台机器上记笔记，不会同步到同事的会话里。它不是你整个职业生涯攒下来的经验与判断，所以那些教训仍得由你写下来，给整支团队用。
- **智能体又积极又自信。**让一个好工程师去做明显不对的事，他会顶回来；智能体更可能照做，而你也更容易过度信任它。沃顿商学院关于「认知让渡」的研究里，受试者多数时候接受了 AI 给的错误答案，而且信心反而更足。要对冲这种过度自信，可以让智能体反过来驳一驳自己的结论。
- **你只有一种智能体原型，而且它每隔几个月就变一次。**人类团队里各有所长；你手里所有智能体的长短处却一模一样，还会随每次模型发布整体漂移。
- **初级工程师还得你来带。**当智能体把新人本来靠它练基本功的入门活接走，你就得作为管理者，有意识地把这些练习机会重新造出来。
- **人的团队依然要紧。**有时候你管了一整天智能体，都没察觉自己把「把团队拧成一股绳」所需的时间挤掉了。别这样。

## 你不需要那个头衔

**最佳实践：**把力气花在让好软件真的发生上：给足上下文、定义清楚「完成」、把评审做扎实。

**反模式：**一边放着交代不清、又没人验收的智能体乱跑，一边还拿代码行数评价自己。

优秀的资深工程师（staff engineer）一直是这么干的：写设计文档、把上下文铺好、评审做到位、让身边人变强。智能体让每个工程师第一天就能这么干。它给你开了一门管理的速成课——反馈以分钟计，而不是以季度计；自己犯的错还能撤回。这份工作正在从「把代码写出来」，变成「成为好代码得以被写出来的那个原因」。

没人天生就是好管理者，好工程师也一样。本事还是老办法练出来的：一遍遍做。只是有了智能体，练的成本变低了。

不妨从这几条开始：

- 每个任务都得配一条它能自己跑的检查，并且向它要证据。
- 只讲它看不见的，它自己看得见的别写。
- 写代码之前，先把计划聊透。
- 同一件事纠了两次？记进 `CLAUDE.md`。反复走的流程？做成 skill。
- 连纠两次没成？重开会话，重写指令。
- 审 diff 时，就当自己半夜会因为它被叫醒。

你大可不必想当管理者。但真把智能体用好的工程师，走着走着，终究会把「怎么管」学会。

> **文中提到的旧文。** [《Your coding agents need a manager》](https://addyosmani.com/blog/coding-agents-manager/) 与 [《Cognitive Surrender》](https://addyosmani.com/blog/cognitive-surrender/) 都是作者本人此前写的；`orchestration tax`（编排税）、`inner / outer loop`（内外层循环）等也是他自造并反复使用的说法。本文可视为产品团队的一线复盘。
>
> **「指南」与 `CLAUDE.md`。** 指 [Claude Code 最佳实践指南](https://code.claude.com/docs/en/best-practices)，文中多处简称「指南」。`CLAUDE.md` 是智能体每次开会话时自动读入的项目指令文件。
>
> **指挥官意图 / context, not control。** 前者是军事术语：只交代目的与意图，不规定具体动作；后者出自 Netflix 文化手册，主张靠共享上下文而非审批流程来对齐。二者说的都是「讲清 what 与 why，放开 how」。
>
> **安迪·格鲁夫《高产出管理》。** Intel 前 CEO 的管理经典。`task-relevant maturity` 指监督强度应按「此人在该具体任务上的过往表现」定，而非按总体资历；文中「有指标就要有制衡指标」也出自这一脉思路。
>
> **Claude Code 的命令与机制。** `/goal`：每轮后由独立模型检查目标条件；Stop hook：回合结束前强制校验；`/code-review`：把 diff 交给未参与对话的新子智能体；`/batch`：把大改动拆成 5～30 个任务、在独立 worktree 并行、各出一个 PR；`/rewind`：回退代码与对话；plan mode：先对齐计划再编码；auto memory：仅本机的笔记。Skills / hooks / subagents / MCP 均为其扩展机制，auto 模式的分类器负责拦截危险动作。
>
> **认知让渡（cognitive surrender）。** 指人把判断交给 AI、甚至对错误答案更自信的现象，文中引的是沃顿商学院相关研究。作者给的对冲办法是让智能体反驳自己的答案。
>
> **编排税 / 管理幅度。** `orchestration tax` 为作者自造词，指每多一个并行智能体带来的额外协调与审查开销；`span of control`（管理幅度）是管理学里一名管理者能有效直接带领的下属数。
>
> **代码追认（code ratification）。** 原文自造的对照词——只是盖章通过，而非真正审查（code review）。
>
> **内层循环 / 外层循环。** 作者常用的一对划分：内层是具体改动怎么实现，外层是约束、验证证据、审批与取舍。本文主张把内层交给智能体，人守住外层。
>
> **其余管理术语。** skip-level manager：隔级管理者，管目标、护栏与各条线负责人，不直接管工程师个人产出；WIP（work in progress）：在制品，限制并行未完事项的数量；probation period：试用期，此处指新流程先有人盯几轮再放手。
>
> **保留原样的部分。** `p95`、`schema`、`API`、`linter`、`diff`、`PR`、`hook`、`worktree`、`skill`、`MCP` 等沿用中文技术圈通行写法；示例指令里的路径、命令与数字均按原文保留，只把说明性文字译为中文。全文论点、数字、举例与章节顺序均照原文，未作增删或改写。
